# AEIB Release Candidate 5 (rc.5) Gate Specification & Operational Readiness Criteria

**Document Status:** Formal Verification Gate Specification  
**Version Target:** `v1.0.0-rc.5` (advancing from `v1.0.0-rc.4-preprod`)  
**Standard Calibration:** DORA (Regulation (EU) 2022/2554) Article 17, EU AI Act High-Risk Execution Boundary, NIST AI RMF 1.0  
**Epistemic Notice:** This specification defines concrete, measurable, and non-bypassable verification criteria evaluated under the stated local verification model. It establishes what must be tested, observed, and independently reproduced before the AEIB prototype scaffold can graduate to `rc.5` or enter controlled institutional pilot deployments.

---

## 1. Executive Context & Purpose

The transition from pre-production prototype (`v1.0.0-rc.4-preprod`) to release candidate (`v1.0.0-rc.5`) marks the transition from isolated component verification to integrated operational assurance. While `rc.4` established internal cryptographic purity, deterministic simulation testing, and local component tests, `rc.5` requires demonstrating that the execution boundary functions reliably across real kernels, genuine hardware attestation roots, clean-room environments, and independent third-party evaluations.

No claim of complete invulnerability, absolute operational security, or universal correctness may be made. Progression to `rc.5` is governed strictly by the binary pass/fail fulfillment of the eight gates defined below.

### Gate 1: Multi-Kernel eBPF LSM Live Attachment & Enforcement

* **Objective:** Verify that kernel-level execution boundaries load, enforce, and detach on real Linux LTS kernels rather than relying solely on userspace emulation.
* **Target Platforms:**
  1. Linux 6.1 LTS (`CONFIG_BPF_LSM=y`, BTF enabled, x86_64 and aarch64).
  2. Linux 6.6 LTS (`CONFIG_BPF_LSM=y`, BTF enabled, x86_64 and aarch64).
* **Mandatory Criteria:**
  1. **Relocatable CO-RE Loading:** All four relocatable LSM probe hooks (`bprm_check_security`, `file_mprotect`, `mmap_file`, `socket_connect`) compile into valid ELF object code (`aeib_lsm.bpf.o`) and pass the kernel in-kernel BPF verifier without rejected instructions.
  2. **Memory Protection Enforcement:** When an agent process attempts an unauthorized memory permission transition (`mprotect` marking writable memory executable, violating W^X), the probe intercepts the syscall and returns `-EACCES` or `-EPERM`.
  3. **Egress Socket Policy:** When an agent process attempts an outbound network connection via `socket_connect` to an IP/port not registered in the CIDR allowlist BPF map (`allowed_egress_map`), the connection is blocked at the LSM layer before TCP SYN dispatch.
  4. **Clean Detachment Lifecycle:** Upon controller shutdown, all attached BPF link handles detach cleanly without leaving dangling hooks, kernel panics, or unreleased pinned map memory.
  5. **Platform Boundary Transparency:** Non-Linux platforms (e.g., macOS Darwin) or non-root environments must be explicitly logged and tagged as running in userspace boundary emulation mode (`is_hardware_ebpf = false`), with zero claim of kernel-level enforcement.
* **Evidence Required:**
  - Automated test execution transcript generated by `crates/aeib-ebpf-lsm/scripts/verify_linux_ebpf_lsm.sh` on both target kernels.
  - Pinned BPF program and map inspection logs (`bpftool prog show`, `bpftool map dump`).

### Gate 2: Hardware-Attested TPM 2.0 / Confidential Computing Quote

* **Objective:** Decouple attestation generation from verification and validate quotes against genuine hardware or virtualized hardware roots of trust.
* **Target Platforms:**
  1. Physical discrete/firmware TPM 2.0 (`/dev/tpmrm0` or `/dev/tpm0`).
  2. Virtual TPM 2.0 (vTPM under KVM/Hyper-V).
  3. Confidential VM Attestation (Intel TDX Quote Generation Service or AMD SEV-SNP Guest Driver).
* **Mandatory Criteria:**
  1. **Certificate Hierarchy Validation:** The Attestation Key (AK) certificate chain is traced to a trusted manufacturer Root Certificate Authority (e.g., Infineon, STMicroelectronics, Nuvoton, or Cloud CSP vTPM CA).
  2. **Cryptographic PCR 11 Extension:** PCR 11 is extended with the SHA-256 hash of the combined eBPF policy map and SCITT Merkle root:
     $$\text{PCR11}_{\text{new}} = \text{SHA-256}(\text{PCR11}_{\text{old}} \parallel \text{digest}(\text{eBPF} \parallel \text{SCITT}))$$
  3. **Fresh Nonce Validation:** Quote generation requires a caller-supplied 32-byte cryptographic nonce (`qualifying_data_nonce`); verifier rejects replayed or stale nonces.
  4. **Standalone Verification Tool:** `tools/verify_tpm_quote.py` validates quotes independently of the generation code, verifying PCR composite hashes and cryptographic signatures over canonical RFC 8785 JCS data.
  5. **Operational Mode Flagging:** Verification receipts must explicitly indicate whether the quote was produced by genuine hardware (`is_hardware_tpm: true`) or an in-memory software simulation (`is_hardware_tpm: false`).
* **Evidence Required:**
  - Standalone verification report produced by `python3 tools/verify_tpm_quote.py --quote <quote_path> --verify`.
  - Stored quote artifact including certificate chain and AK public key.

### Gate 3: Clean-Clone Hermetic CI Conformance & Signed Release Artifacts

* **Objective:** Prove that the entire verification suite executes cleanly from a fresh checkout in an isolated environment without relying on developer-local artifacts.
* **Target Platforms:** Hermetic CI containers (Ubuntu 24.04 LTS and macOS 14/15 runner).
* **Mandatory Criteria:**
  1. **Clean-Room Clone:** CI checks out repository at the target commit into an empty workspace with no pre-existing target directories or caches.
  2. **AST Static Analysis:**
     - `compliance/check_zone_boundary.py` confirms zero boundary leaks between Zone 1 and Zone 2.
     - `compliance/ast_purity.py` and `compliance/no_mock_enforcer.py` confirm zero mocks, stubs, or dynamic bypass primitives across all production and test source code.
     - `compliance/aeib_p3c_ast_gate.py` confirms absence of forbidden runtime execution calls.
  3. **Multi-Crate Compilation:** Cargo builds `crates/aeib-ebpf-lsm`, `crates/smaos-verify`, and root workspace without errors or unvetted dependencies.
  4. **Cryptographic Signing of Release Assets:** All generated distribution artifacts (WASM binary, CBOM manifest, evidence hashes, and decision packs) are signed with the repository release Ed25519 key, with signatures verifiable via `tools/standalone_receipt_verifier.py`.
* **Evidence Required:**
  - Green CI execution run logs from `.github/workflows/aeib_conformance_ci.yml`.
  - Output manifest `output/evidence-hashes.txt` signed and committed.

### Gate 4: Deterministic, Bit-for-Bit Reproducible WebAssembly Provenance

* **Objective:** Ensure the client-side/auditor verification runtime (`smaos_verify.wasm`) can be compiled independently by any party and yield the identical binary digest.
* **Mandatory Criteria:**
  1. **Dual Independent Build Verification:** Two independent builds executed on distinct filesystems using `scripts/build_reproducible_wasm.sh` must produce the identical SHA-256 hash:
     ```
     6ecc360af19008632c950d94910b70220e3c2cc36a5cc29fe0c33ba64d2bb041
     ```
  2. **Pinned Toolchain & Flags:** Compilation uses pinned `rustc 1.95.0`, target `wasm32-unknown-unknown`, profile `opt-level = "z"`, and link-time optimization (LTO) enabled.
  3. **In-Toto / SLSA Provenance Statement:** `evidence/wasm_build_provenance.json` records the exact compiler metadata, cargo lockfile hash, source commit, and output binary hash.
  4. **Runtime Conformance Suite:** The compiled WASM binary passes all 8 test vectors in `tests/test_smaos_verify_wasm.js` executed under native Node.js V8 runtime.
* **Evidence Required:**
  - Output log from `scripts/build_reproducible_wasm.sh` displaying matching hash verification.
  - Successful test run output from `node tests/test_smaos_verify_wasm.js`.

### Gate 5: Formally Approved DORA Article 17 Governance & Operating Architecture

* **Objective:** Provide the complete institutional governance framework required for financial entity deployment under Regulation (EU) 2022/2554 (DORA).
* **Mandatory Criteria:**
  1. **STRIDE Threat Model:** `docs/governance/DORA_ART17_THREAT_MODEL_STRIDE.md` documents 7 assets across 4 trust boundaries, delineating residual risks and out-of-scope conditions.
  2. **Change Management & RACI Matrix:** `docs/governance/DORA_ART17_CHANGE_MANAGEMENT_AND_RACI.md` defines the 5 operational roles, 7-stage change procedure, emergency bypass protocols, and verified component rollback RTOs ($< 120\text{s}$).
  3. **Incident Management Runbook:** `docs/governance/DORA_ART17_INCIDENT_MANAGEMENT_RUNBOOK.md` establishes SEV-1/2/3 criteria aligned with RTS 2025/301, automated circuit-breaker trips, and forensic root-cause analysis procedures.
  4. **Key Management & Cryptographic Custody Policy:** `docs/governance/KEY_MANAGEMENT_AND_CRYPTOGRAPHIC_CUSTODY_POLICY.md` establishes HSM custody boundaries, 2-of-3 multi-party authorization for supervisor warrants, and NIST FIPS 204 ML-DSA migration paths.
  5. **Vulnerability & Dependency Management Policy:** `docs/governance/VULNERABILITY_MANAGEMENT_POLICY.md` formalizes vulnerability scanning SLAs, dependency vetting rules, and software supply chain disclosures.
* **Evidence Required:**
  - Completed and linted governance pack in `docs/governance/`.
  - Zero promotional or uncalibrated terms across all governance documents.

### Gate 6: Adversarial Negative Invariant & Property-Based Fuzzing Battery

* **Objective:** Subject all parser, boundary, and state-machine components to systematic adversarial perturbation to prove fail-closed operation under fault and attack conditions.
* **Mandatory Criteria:**
  1. **RFC 8785 Canonical JCS Fuzzing:** 100 iterations of structural JSON corruptions (whitespace injection, unsorted UTF-16 code units, number representation edge cases) must be rejected with deterministic verification failures.
  2. **RFC 9162 Merkle Proof Bit-Flipping:** 50 single-bit corruptions across Merkle tree node hashes and direction flags must fail closed without false positives.
  3. **Ed25519 Signature Corruption:** 50 corrupted signature vectors across authorization grants and transparency receipts must be rejected.
  4. **UnitBoost Conflict Resolution:** 50/50 multi-agent conflicting slot proposals must resolve to `RESIDUAL_UNCERTAINTY` and trigger `UNCERTAINTY_HALT` rather than arbitrary tie-breaking.
  5. **Secure UDS Boundary Interception:** Ephemeral Unix Domain Socket tests verify that TCP localhost connections, mismatched peer UIDs, recycled PIDs, and out-of-scope capability tokens are rejected fail-closed.
  6. **Empirical Latency Budget:** Gate execution overhead under 100 continuous iterations must remain within operational bounds:
     - $\text{p50} \le 0.050\text{ ms}$
     - $\text{p95} \le 0.100\text{ ms}$
     - $\text{p99} \le 0.500\text{ ms}$
* **Evidence Required:**
  - Automated test run transcript from `tests/test_adversarial_fuzz_and_negative_invariants.py`.
  - Benchmark latency summary JSON from `benchmarks/aeib_execution_integrity/`.

### Gate 7: Automated Backup Restorability, Cryptographic & Git Integrity Checks

* **Objective:** Validate that physical off-site backup storage can be restored into a clean environment, verifying artifact hashes, WebAssembly execution, and full git repository integrity.
* **Mandatory Criteria:**
  1. **Automated Clean-Room Restoration:** `compliance/backup_restorability_verifier.py` restores critical artifacts and git database from external backup (`/Volumes/EXTssd/SovereignNexus_Backup`) into an isolated temporary directory.
  2. **Cryptographic Manifest Verification:** All restored files are hashed and verified bit-for-bit against `output/evidence-hashes.txt`.
  3. **Restored WASM Conformance:** Restored `smaos_verify.wasm` is instantiated in an isolated Node.js runtime and successfully executes baseline verification.
  4. **Git Repository Object Integrity:** Restored repository passes `git fsck --full` with zero corrupt objects, dangling references, or broken commit trees.
  5. **Empirical RTO Measurement:** Measured restoration time must satisfy the operational SLA ($< 60\text{s}$, observed $< 1\text{s}$).
* **Evidence Required:**
  - Generated receipt in `output/backup-restorability-receipt.json` with `restorability_verified: true` and `git_fsck_verified: true`.

### Gate 8: Independent Second-Party Clean Reproduction Receipt

* **Objective:** Eliminate single-party bias by having an independent party or distinct environment execute the reproduction suite and generate a verifiable receipt.
* **Mandatory Criteria:**
  1. **Automated Reproduction Script:** `scripts/clean_reproduction.sh` executes end-to-end from clone to verification receipt generation with exit code 0.
  2. **Independent Hardware/Runner:** Executed on a machine separate from the primary development environment.
  3. **Signed Reproduction Statement:** Second party generates an RFC 8785 JCS receipt recording git commit hash, environment configuration, test durations, and SHA-256 digests of all evaluated outputs, signed with their own key.
  4. **Zero Test Divergence:** All 500 deterministic DST episodes, Python property tests, Rust unit tests, and Node.js WASM vectors must match expected outcomes without modification.
* **Evidence Required:**
  - Committed reproduction statement: `evidence/reproduction_receipt_second_party.json`.

## 4. Operational Transition Boundary

Upon completion and verification of Gates G-1 through G-8, the system advances to tag `v1.0.0-rc.5`. Graduation from `rc.5` to an initial production deployment requires subsequent live partner integration testing, deployment within a regulated financial entity sandbox, and approval by designated institutional compliance and risk authorities.
