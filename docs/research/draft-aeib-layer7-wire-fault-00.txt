        Agent Evidence Interlock Boundary (AEIB): Layer 7 Wire-Fault Profile
                   draft-aeib-layer7-wire-fault-00

Abstract

   This document defines the Layer 7 Wire-Fault Profile for the Agent
   Evidence Interlock Boundary (AEIB). It specifies the deterministic
   handling of mid-flight transport anomalies (e.g., HTTP 504 Gateway
   Timeout, TCP RST) for autonomous agents interacting with external
   APIs. By establishing a fail-closed structural boundary and a strict
   reconciliation protocol, this profile mitigates the "HTTP 200 Illusion"
   and suppresses un-gated speculative retries, designed to mitigate
   uncoordinated duplicate mutations under the stated fault model.

1.  Introduction

   Autonomous systems invoking remote state-mutating APIs frequently
   encounter mid-flight transport faults (e.g., HTTP 504, TCP RST).
   When a fault occurs after the payload has been dispatched but before
   the transport layer confirms the HTTP 200 OK response, the actual
   state of the remote provider is indeterminate.

   Current autonomous agents frequently default to a "retry-safe"
   assumption, leading to duplicate side effects (as evaluated in
   Li, arXiv:2609.29095). This document specifies the AEIB protocol,
   which forces a fail-closed "retry_safe: false" interlock during
   such transport faults until out-of-band reconciliation resolves state.

3.  The L7a Transport Capture

   An AEIB-compliant gateway MUST trap network socket state changes.
   If a connection terminates unexpectedly prior to the completion
   of the application-layer HTTP response, the gateway MUST yield a
   transport_observation of "DISPATCHED_UNCONFIRMED".

4.  The L7c Disposition Mapping

   Upon receiving a "DISPATCHED_UNCONFIRMED" observation, the engine
   MUST NOT yield an "OUTCOME_VERIFIED" disposition. Instead, the
   engine MUST query the out-of-band probe (L7b). If the probe fails to
   reconcile the state within the consistency grace period, the engine
   MUST yield "EFFECT_INDETERMINATE" and set "retry_safe: false".

5.  Security & Human Oversight Considerations

   The AEIB protocol relies on structural verification of the filesystem
   and Git state (e.g., via the Tycho offline verifier) to prevent the
   "HTTP 200 Illusion" where compromised APIs return false successes.
   Receipts SHOULD be signed using FIPS 204 compliant PQC algorithms
   (e.g., ML-DSA-65 or ML-DSA-87) alongside Ed25519 in COSE envelopes.

   To mitigate cognitive memory distortion induced by generative model
   summarization (empirically evaluated in Sim et al., arXiv:2609.28820),
   human oversight review gates MUST inspect raw RFC 8785 canonical
   JSON receipts directly without intermediary AI summarization.
