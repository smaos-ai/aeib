# Phase 4: A2A Handshake & Authentication Negotiation — Design Specification

> **Architectural Status:** APPROVED
> **Date:** 2026-05-10
> **Scope:** Discovery, attestation-based trust evaluation, session establishment

---

## 1. Overview

Phase 4 enables external agents to discover SISS personas and establish authenticated sessions through a cryptographically-grounded handshake protocol. The protocol is built on three pillars:

1. **Passive Discovery**: External agents discover SISS personas via GET /.well-known/agent.json (Google A2A Agent Card format)
2. **Attestation-Based Trust**: External agents prove trustworthiness by presenting cryptographic evidence (hardware enclave validation, model integrity, sovereign origin, runtime integrity)
3. **Deterministic Capability Provisioning**: SISS evaluates attestations against stored TrustPolicyNode, assigns a security tier, and grants scoped credentials (session token + capability token)

---

## 2. Discovery Endpoint: GET /.well-known/agent.json

**Purpose**: External agents discover SISS personas and learn what authentication schemes they support.

**Response**: Google A2A Agent Card JSON (generated by Phase 3 siss-agent-card crate)

```json
{
  "name": "SISS-Persona-Name",
  "description": "Sovereign Internet-Scale System persona",
  "version": "1.0.0",
  "url": "https://siss.example.com",
  "skills": [
    {
      "id": "tool_execution",
      "name": "Tool Execution",
      "description": "Execute authorized tools",
      "tags": ["medium"]
    }
  ],
  "capabilities": {
    "streaming": true,
    "push_notifications": false
  },
  "authentication": {
    "schemes": ["Bearer", "OAuth2", "mTLS", "SignedChallenge"]
  }
}
```

**External agent workflow**:
1. GET /.well-known/agent.json
2. Parse response, identify supported auth schemes
3. Determine which scheme(s) it can satisfy
4. Proceed to handshake endpoint

## 3. Handshake Endpoint: POST /.well-known/a2a/handshake

### 3.1 Request Payload

External agent initiates handshake by POST-ing its identity, supported schemes, and cryptographic attestations:

```json
{
  "agent_card": {
    "name": "ExternalAgent-v2.5",
    "description": "Trusted external AI agent",
    "version": "2.5.0",
    "url": "https://external-agent.example.com",
    "capabilities": {
      "streaming": true,
      "push_notifications": false
    }
  },
  "auth_schemes_supported": ["Bearer", "OAuth2", "mTLS", "SignedChallenge"],
  "attestations": [
    {
      "type": "hardware_enclave",
      "format": "sgx_quote",
      "payload": "<base64-encoded SGX quote>",
      "signature": "<signature-over-quote>",
      "issuer": "intel-sgx-signer",
      "issued_at": "2026-05-10T14:32:00Z",
      "valid_until": "2026-05-10T18:32:00Z"
    },
    {
      "type": "model_integrity",
      "format": "signed_manifest",
      "payload": "<base64-encoded model manifest + weights hash>",
      "signature": "<signature-from-model-publisher>",
      "issuer": "anthropic",
      "issued_at": "2026-05-09T00:00:00Z",
      "valid_until": "2026-06-09T00:00:00Z"
    }
  ]
}
```

**Attestation Types** (external agent can present any subset):

1. **hardware_enclave** — Proof agent runs in SGX/TEE
   - Payload: SGX quote or TPM attestation report
   - Issuer: `intel-sgx-signer`, `arm-tee`, `amd-sev`, etc.
   - SISS validates: Enclave measurement hash against TrustPolicyNode allowlist

2. **model_integrity** — Proof of unmodified model weights
   - Payload: Model ID + version + SHA256(weights) + signature
   - Issuer: Model publisher (e.g., `anthropic`, `openai`)
   - SISS validates: Hash + publisher signature against known-good model versions in policy

3. **sovereign_origin** — Proof of deployment jurisdiction
   - Payload: Deployment location + timestamp + jurisdiction certificate
   - Issuer: Deployment verifier or cloud provider
   - SISS validates: Jurisdiction against allowed/denied list in policy

4. **runtime_integrity** — Proof of unmodified runtime environment
   - Payload: OS version + container image hash + dependency manifest + signature
   - Issuer: Runtime verifier or container platform
   - SISS validates: Runtime hash against allowed baselines in policy

### 3.2 Response Payload (Success Case)

After validating attestations against TrustPolicyNode and assigning a security tier, SISS responds with:

```json
{
  "status": "authenticated",
  "selected_scheme": "Bearer|OAuth2|mTLS|SignedChallenge",
  "session_token": {
    "token": "<jwt-or-opaque-credential>",
    "expires_in": 3600,
    "token_type": "Bearer"
  },
  "capability_token": {
    "token": "<signed-capability-envelope>",
    "delegations": [
      {
        "permission": "can_execute",
        "resource_type": "tool",
        "resource_ids": ["tool-uuid-1", "tool-uuid-2"],
        "constraints": {
          "rate_limit": "1000/minute",
          "max_concurrent": 5,
          "allowed_hardware": ["LocalMlx", "Hybrid"]
        }
      }
    ],
    "issued_at": "2026-05-10T14:32:00Z",
    "valid_until": "2026-05-11T14:32:00Z"
  },
  "trust_policy_requirements": {
    "minimum_security_tier": 2,
    "required_capabilities": ["streaming"],
    "attestation_required": false
  }
}
```

**Token Semantics**:
- **session_token**: Operational authentication credential. External agent includes in `Authorization: Bearer <token>` header on subsequent API calls. SISS validates signature/issuer on each request.
- **capability_token**: Authorization envelope defining what external agent is allowed to do. Lists tool delegations, rate limits, hardware constraints, expiry. Signed by SISS; external agent presents it when invoking tools.

---

### 3.3 Response Payload (Failure Cases)

**Case 1: Agent Classification Denied**
```json
{
  "status": "denied",
  "reason": "agent_id_blacklisted",
  "detail": "Agent UUID matches denied_agents_by_id in trust policy"
}
```

**Case 2: Required Attestation Missing**
```json
{
  "status": "denied",
  "reason": "missing_required_attestation",
  "missing_attestations": ["hardware_enclave"],
  "detail": "This persona requires hardware enclave attestation"
}
```

**Case 3: Attestation Validation Failed**
```json
{
  "status": "denied",
  "reason": "attestation_validation_failed",
  "failed_attestation_type": "model_integrity",
  "detail": "Model signature verification failed against trusted publishers"
}
```

**Case 4: Security Tier Below Minimum**
```json
{
  "status": "denied",
  "reason": "insufficient_security_tier",
  "required_tier": 2,
  "calculated_tier": 3,
  "detail": "Attestation evidence grants tier 3; persona requires minimum tier 2"
}
```

## 5. Trust Evaluation Algorithm

When SISS receives handshake request with attestations:

### 5.1 Agent Classification Check
```
if agent_id in denied_agents_by_id → DENY
if agent_type not in allowed_agent_types → DENY
if agent_organization not in allowed_organizations → DENY
else → proceed to attestation validation
```

### 5.2 Attestation Validation & Scoring
```
failed_count = 0
attestation_score = 0

for each required_attestation_spec in policy:
  if (required_attestation_spec.required == true):
    if (attestation NOT in request) → failed_count++
  
  if (attestation in request):
    validate_signature(attestation, issuer_key_from_graph)
    validate_freshness(attestation, required_attestation_spec.max_attestation_age_seconds)
    validate_type_specific_constraints(attestation, required_attestation_spec)
    
    if all validations pass:
      attestation_score += points_for_type(attestation.type)
    else:
      failed_count++

if failed_count > policy.max_failed_attestations → DENY
else → proceed to tier assignment
```

**Attestation Point Values** (subject to policy):
- hardware_enclave: +50 points
- model_integrity: +30 points
- sovereign_origin: +20 points (jurisdiction-specific)
- runtime_integrity: +20 points

### 5.3 Security Tier Assignment
```
if attestation_score >= tier_1.required_attestation_score → tier = 1
else if attestation_score >= tier_2.required_attestation_score → tier = 2
else if attestation_score >= tier_3.required_attestation_score → tier = 3
else → DENY (insufficient_security_tier)
```

### 5.4 Capability Grant
```
granted_capabilities = tier.allowed_capabilities
granted_rate_limits = tier.rate_limits
granted_resource_classes = tier.allowed_resource_classes
denied_tools = tier.denied_tools
```

### 5.5 Delegation Construction
```
for each tool in persona.allowed_tools:
  if tool in denied_tools → skip
  if tool.risk_class in allowed_resource_classes → include
  
  apply rate_limits from tier
  apply max_concurrent_executions from delegation_constraints
  apply allowed_hardware_targets from delegation_constraints

capability_token.delegations = [all included tools + constraints]
```

### 5.6 Token Emission
```
session_token.expires_in = delegation_constraints.token_expiry_seconds.session_token
capability_token.valid_until = now + delegation_constraints.token_expiry_seconds.capability_token

return {
  status: "authenticated",
  selected_scheme: chosen_from_auth_schemes_supported,
  session_token,
  capability_token,
  trust_policy_requirements
}
```

## 6. Auth Scheme Selection (Deterministic)

When multiple schemes are supported by both SISS persona and external agent, SISS chooses via three-layer filtering:

1. **Trust Policy Filter**: Remove schemes not in `allowed_schemes` (if policy specifies any)
2. **Security Tier Filter**: Remove schemes below tier's `minimum_scheme_strength`
3. **Preference Order**: Choose highest-ranked remaining scheme

Example:
```
policy.allowed_schemes = ["Bearer", "mTLS"]
persona.supported_schemes = ["Bearer", "OAuth2", "mTLS", "SignedChallenge"]
agent_supported_schemes = ["Bearer", "mTLS"]

intersection = ["Bearer", "mTLS"]
after_policy_filter = ["Bearer", "mTLS"]
after_tier_filter = ["Bearer", "mTLS"]
selected = first_in_preference_order = "Bearer"
```

## 7. Subsequent Authenticated Requests

After handshake succeeds, external agent uses session token on all subsequent requests:

```http
GET /api/tools HTTP/1.1
Authorization: Bearer <session_token>
X-Capability-Token: <capability_token>
```

SISS validates on each request:
1. session_token signature + issuer + expiry
2. capability_token signature + expiry
3. Requested operation is in capability_token.delegations
4. Rate limits not exceeded
5. Audit log the request

## 9. Design Decisions Rationale

**Why TrustPolicyNode is graph-native (not config files)?**
- Allows per-persona, multi-tenant policy isolation
- Supports runtime policy updates without redeployment
- Integrates with existing Knowledge Graph audit trail

**Why attestation score (not binary pass/fail)?**
- Provides nuance: "We prefer TEE + model signature, but accept TEE alone"
- Enables gradual trust elevation (future: refresh attestations to boost score)

**Why session token + capability token (not one combined token)?**
- Separation of concerns: authentication (can you prove identity?) vs authorization (what can you do?)
- Enables token rotation: refresh session token without revoking capabilities
- Supports delegation chains (future: capability token can be sub-delegated)

**Why handler in siss-agent-card (not separate crate)?**
- Handshake is tightly coupled to Agent Card discovery
- Reduces inter-crate complexity; keeps A2A protocol logic colocated
